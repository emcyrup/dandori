# ナイトだんどり　本番サーバー配備手順

対象：`https://dandori.olivia.ai-labo.cloud` → サーバーの nginx（https）→ `127.0.0.1:8032`
サーバー：Ubuntu / Node 22 / PostgreSQL 18、**sudo なし・Docker なし**（ホームディレクトリ内だけで動かす）
DB：`dandoriolivia`（ユーザー `ai_labo_dbuser`）

```
 ブラウザ / LINE
     │ https://dandori.olivia.ai-labo.cloud
     ▼
 サーバーの nginx（https・提供元が管理）
     │ 127.0.0.1:8032
     ▼
 PM2 が動かすプロセス（~/dandori/server）
   gateway    入口。画面（1_画面）を出し、API を下の部品へ振り分ける   Node
   rest       データの受け口（PostgREST、単体バイナリ）                 :38032
   auth       ログイン（GoTrue、単体バイナリ）                          :38033
   storage    ファイル置き場（server/data/storage に保存）              Node :38034
   fn-*       3_サーバー の5つの関数（Deno）                            :38041〜
   outbox     送信箱を5分ごとに送る（任意）
     │
     ▼
 PostgreSQL（同じサーバー）dandoriolivia
```

Supabase の `supabase.js`（画面側）はそのまま使えます。`config.js` の接続先は、入口が自動でこのサーバーに向けて出すので、
リポジトリの `config.js` を書き換える必要はありません。

### Supabase との違い

| | Supabase | このサーバー |
|---|---|---|
| ログイン / データの受け口 | クラウド | 同じ部品（GoTrue / PostgREST）を手元で動かす |
| ファイル置き場 | Storage | 小さな自前の実装（`server/storage`）。アプリが使う操作だけ対応 |
| Edge Functions | Deno（クラウド） | Deno（単体バイナリ）で同じコードを動かす |
| 定期送信（pg_cron） | DB 内 | PM2 の5分ごと起動（`.env` の `OUTBOX=1`） |
| 管理画面 / SQL Editor | あり | `./db.sh sql "…"` / `./db.sh psql` |
| service_role の RLS 素通り | あり | 無いので、SQL を流すたびに `post.sql`（単一ロールでは `pre-single.sql` → SQL → `post-single.sql`）で代わりの許可を足す（`db.sh schema` が自動で行う） |

## DB の役割（ロール）が作れないサーバーについて ― 単一ロールモード

Supabase と同じ部品は本来、anon / authenticated / service_role などの役割を使います。
提供元の方針で役割が作れない場合、配備スクリプトが自動で **単一ロールモード**（`.env` に `DB_MODE=single`）に切り替え、
DB のユーザー1つ（`ai_labo_dbuser`）だけで動かします。手順 0 は不要です。

このモードでも「だれが何を見られるか」は Supabase と同じに保っています：
- すべての表に、持ち主にも RLS が効く設定（FORCE ROW LEVEL SECURITY）を付ける
- 画面から直接の読み書きは、ログインした方の法人・店舗のぶんだけ（匿名は何も見えない）
- 関数（security definer）の中は Supabase と同じく RLS を素通り（`application_name` を印に使う）
- サーバー処理の鍵は、鍵の中の `"svc":true` で見分けて全件 OK

確認済み：匿名は表を読めない・書けない、店長は自法人だけ、他法人への書き込みは拒否、
サーバー鍵は全件、店長以上だけの関数は匿名から呼べない、書類は自法人のフォルダだけ。

## 0. 先に、DB 管理者（サーバー提供元）に頼むこと（役割を作ってもらえる場合）

配布された `ai_labo_dbuser` は役割（ロール）を作れないので、**`db/依頼_DB権限.sql`** を渡して、
次のどちらかをお願いしてください。

- A（簡単）：`ALTER ROLE ai_labo_dbuser CREATEROLE;` を一時的に付けてもらう（初期設定後に外して可）
- B：`db/依頼_DB権限.sql` を superuser で流してもらう（パスワード3つは `.env` の値を別途伝える）

あわせて確認：`dandoriolivia` の持ち主が `ai_labo_dbuser` であること、サーバーから
`github.com`・`esm.sh`・`api.line.me`・各 AI の API に外向きの通信ができること。

## 店舗ごとの環境について

1店舗 = GitHub の Environment 1つ ＝ サーバー上のフォルダ1つ（`~/dandori-<店舗>`）＝ DB 1つ です。
店舗だけの設定（お店・メニュー・キャスト・給与）は `stores/<店舗>/store.sql` に置き、
全店共通の `2_データベース` のあとに流れます。新しい店舗の増やし方は `stores/README.md` を見てください。
いま配備する店舗は **olivia** です。

## 1. GitHub Actions で配備する（ふだんはこれだけ）

`main` に変更が入ると、`.github/workflows/deploy-server.yml` がサーバーへ SSH でつなぎ、
ソースを送って `install.sh → setup.sh → deploy.sh --auto` を実行します（初回は自動で `--init` 相当）。
`2_データベース` に変更があった push では、SQL も流します。

### 初回だけ：GitHub に店舗の Environment を作り、鍵と設定を登録する

リポジトリの **Settings → Environments → New environment**。名前は店舗名（`olivia`）。その中に：

| 種類 | 名前 | 値 |
|---|---|---|
| Secret | `SERVER_SSH_KEY` | 配布された秘密鍵 `id_rsa_3piece4-prod.pem` の中身（`-----BEGIN` から `END-----` まで全部） |
| Secret | `DB_PASSWORD` | 配布資料の DB パスワード |
| Secret（任意） | `SMTP_USER` `SMTP_PASS` `SMTP_ADMIN_EMAIL` | パスワード再設定メールを使うなら（SES の SMTP 認証情報） |
| Secret（任意） | `ANTHROPIC_API_KEY` `GEMINI_API_KEY` `OPENAI_API_KEY` `PIXABAY_API_KEY` | Supabase の Functions Secrets に入れていた鍵 |
| Variable | `SERVER_HOST` `SERVER_USER` `SERVER_DIR` `SITE_URL` `LISTEN_PORT` `DB_NAME` | olivia は既定値あり（`15.168.86.215` / `3piece_prod4` / `dandori-olivia` / `https://dandori.olivia.ai-labo.cloud` / `8032` / `dandoriolivia`）。2店舗目からは必ず入れる |
| Variable（推奨） | `SERVER_HOST_KEY` | サーバーのホスト鍵 1 行。手元で `ssh-keyscan -t ed25519 15.168.86.215` と打って出た行をそのまま貼る。入れておくと、なりすましサーバーに鍵やパスワードを送らない（無いと初回取得で信じる＝従来どおり。ログに警告が出る） |

配備する店舗の一覧は、リポジトリの Variables の `STORES`（例 `olivia,second`）。無ければ `olivia` だけ。店舗名は英小文字・数字・`-` だけ（それ以外が入っていると配備は止まります）。
**Actions → deploy-server → Run workflow** で手動実行できます（店舗名を入れればその店舗だけ、`run_sql` にチェックで SQL も流す）。

### 実行の流れ（ログで見える順）

1. 文法チェック
2. SSH 接続の確認（`接続OK: 3piece_prod4@…` と出る）
3. ソースを送る（`~/dandori-olivia` に展開。`server/.env` `data/` `logs/` `bin/` は残る）
4. Secrets を `.env` に流し込む → `setup.sh`（鍵は初回に自動生成、2回目からは変えない）
5. `install.sh`（部品の取得。初回だけ数分）
6. `deploy.sh --auto`（初回：DB 初期設定 → 起動 → SQL 全部（共通 → 店舗） → 確認）
7. 公開 URL が 200 を返すか

手順 0 の DB 権限が無いと、6 で「`db/依頼_DB権限.sql` を管理者に」と出て止まります。

## 2. 手で配備する場合（SSH で入って）

```bash
cd ~/dandori-olivia/server   # GitHub Actions が送ったもの（無ければ git clone して .env の STORE を書く）
./install.sh
./setup.sh && vi .env && ./setup.sh     # DB_PASSWORD などを入れる
./deploy.sh --init
```

## 4. 外のサービスの設定

- LINE：**設定（admin.html）→「AI・送信」→「LINEで送る」** に Webhook URL が表示されます（`…/functions/v1/line-webhook?t=（法人ID）`。「コピー」で写せます）。
  同じ欄で **チャネルアクセストークン**（送信用）と **チャネルシークレット**（受信の署名確認用。無いと受信が動きません）を入れてください。
  LINE Developers → Messaging API 設定 → Webhook URL に貼り、「Webhookの利用」をオンに。法人IDは `./db.sh sql "select id, name from public.tenant"` でも見られます
- 送信箱の自動送信を使うなら `.env` に `OUTBOX=1` → `./deploy.sh`
- 提供元の nginx 側（8032 への転送）に次があるか確認してもらう：
  `client_max_body_size 50m;`（ファイルのアップロード）、`proxy_read_timeout 150s;`（AI の下書き）、
  `proxy_set_header X-Forwarded-Proto $scheme;`、
  `proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;`（不正アクセスの検知で接続元を見分けるのに必要）

## ふだんの運用（`~/dandori-olivia/server` で）

| やりたいこと | コマンド |
|---|---|
| 画面・3_サーバー・SQL を直した | `main` に push するだけ（GitHub Actions が配備） |
| 手で入れ替えたい | `./deploy.sh` / SQL は `./deploy.sh --sql ファイル.sql` |
| SQL を1文流す / 対話 | `./db.sh sql "select …"` / `./db.sh psql` |
| 状態を見る | `./deploy.sh --status`（PM2 のプロセス名は `olivia-gateway` のように店舗名付き） |
| ログを見る | `./node_modules/.bin/pm2 logs` または `tail -f logs/*.log` |
| 止める | `./deploy.sh --stop` |

バックアップ：DB は提供元が自動ダンプ + AWS Backup（7日）を行う方針とのこと。
**`server/data/storage/`（ファイル）と `server/.env`（鍵。無くすと全員ログイン不可）** は、こちらで控えを取ってください。

## 不正アクセスの見張り

入口（gateway）がすべての通信を見ていて、見つけたら記録し、その接続元（IP）をしばらく止めます（429 を返す）。
店舗ごとに環境が分かれているので、店舗ごとに独立して働きます。設定は要りません。

| 見つけるもの | 目安 | 止める時間 |
|---|---|---|
| ログイン失敗の連続（同じ接続元） | 10分に5回 | 15分 |
| 同じメールへのログイン失敗の連続 | 10分に10回 | 記録のみ（重要） |
| 壊れた・期限切れの鍵での呼び出し | 10分に20回 | 30分 |
| 管理画面などを探す動き（/wp-admin, .php, .env, .git …） | 10分に3回 | 1時間 |
| サーバーの鍵（service_role）を外から使う | 1回 | その場で拒否 ＋ 24時間 |
| 短時間の大量アクセス | 1分に600回 | 5分 |

- 見る・解除する：**設定 → 不正アクセス**（店長以上）。記録は DB の `security_event`、遮断は `security_block`（90日で自動削除）
- ログ：`server/logs/security.log`。`./deploy.sh --status` にも 24 時間の件数が出ます
- お店の固定 IP など、絶対に止めたくない接続元は `.env` の `SECURITY_ALLOW_IPS=1.2.3.4,5.6.7.8`。止めるのをやめるなら `SECURITY=0`（どちらも `./deploy.sh` で反映）
- 目安は `.env` の `SEC_LOGIN_FAILS` `SEC_EMAIL_FAILS` `SEC_BAD_TOKENS` `SEC_SCAN_HITS` `SEC_FLOOD_PER_MIN` で変えられます
- 接続元は nginx が付ける `X-Forwarded-For` の最後の値で判断します（先頭は偽装できるため）。127.0.0.1（中の部品）は止めません。
  nginx が `X-Forwarded-For` を付けていない通信（ブラウザからのように見えるもの）は「外から」として扱い、サーバー鍵の利用などは拒否します。
  nginx に `proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;` が入っているか、提供元に確認してください（`依頼_サーバー管理者へ.md`）

## 守りの仕組み（脆弱性診断 2026-10 で見直したところ）

- 入口（gateway）：`X-Frame-Options` / `Content-Security-Policy` / `HSTS` などのヘッダー、受け取る本文の上限（ログイン 64KB・データ 8MB・関数 2MB）、
  サーバー鍵の外からの利用拒否、表・関数の一覧（OpenAPI）の非公開
- ファイル置き場：画像・PDF・動画・音声以外は「ダウンロード」扱い（HTML などをサイトの中で開かせない）
- DB：一般スタッフは業務の表（キャスト・伝票・給与など）を画面から直接は書けない（RPC だけ）。名簿の役割・ログインの紐づけは専用の操作だけ。
  サーバー専用の関数（ログイン紐づけ・LINE Webhook）は画面から呼べない。取り込みファイル（imports）は店舗ごとに分離。
  1つの問い合わせは 8 秒まで（`035_security_fixes.sql` と `post-single.sql`）
- 配備：店舗名の形式チェック、鍵やパスワードは標準入力で渡す（ps に出ない）、`SERVER_HOST_KEY` でホスト鍵の固定

## 困ったとき

- `関数 502`：Deno が初回に esm.sh からライブラリを取得中。1〜2分待って `./deploy.sh --status`。
  それでも駄目なら `tail logs/fn-ai.log`（外向き通信が止められていないか）
- `ログイン 502`：`tail logs/auth.log`。DB の役割 `supabase_auth_admin` のパスワードが `.env` と違うことが多い
- ポートがぶつかる（`EADDRINUSE`）：`.env` の `REST_PORT` などを変えて `./deploy.sh`
- `role "anon" does not exist`：手順 0 がまだ
- お店の方が「しばらくの間、この接続元からの利用を止めています」と出て入れない：設定 → 不正アクセス で解除。
  同じ回線で何人もログインに失敗すると起きます。固定 IP なら `SECURITY_ALLOW_IPS` に入れておく
- ログインや画面で `stack depth limit exceeded`：SQL の流し直しが途中で止まり、仕上げ（post-single.sql）が流れていない。
  `./db.sh schema` をもう一度流す（単一ロールモードでは流す前に FORCE RLS を外す pre-single.sql が自動で入る。
  その間だけ API を止めるので、画面は1分ほど「接続できません」になる）


## ログインの権限と、スタッフの LINE 連携（2026-10-26〜）

- 権限は **店長（管理者）** と **スタッフ** の2つです（中の値は owner / staff）。店長が「設定 → 権限」で、店長・スタッフそれぞれが使える機能を決めます。
  お金の全体像（給与の計算・月別・照合・キャスト設定）と、設定・ログインの管理は、データベースでも店長だけに閉じています。
- スタッフの LINE をアプリにつなぐには：お店の LINE を友だち追加 → 店長の **認証コード**（「届出・許可証 → LINEの登録」に表示。6けた）をトークに送る →
  つづけてログインのメールアドレスか名簿のお名前を送る。5回まちがえた LINE は1時間止まります。コードは同じ画面の「新しくする」で変えられます。
